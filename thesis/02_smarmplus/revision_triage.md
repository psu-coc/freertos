1. **DMA → handled by GTZC.**
   - Cite VECODI (Kiri, Nunes, Francillon, Rattanavipanon, arXiv 2606.07470, §3.1). It assumes "a security DMA controller capable of specifying DMA access permissions for memory regions, such as the Global TrustZone Controller (GTZC) available on our NUCLEO-L552ZE-Q", which is the same board as ours.
   - PEARTS (§4, Initialization) offers an extra option: the Secure World checks whether any DMA channel is configured to write into the protected range.
   - Our firmware already calls `MX_GTZC_S_Init()` (MPCBB on SRAM1/SRAM2) and routes `GTZC_IRQn` (illegal-access IRQ) to the Secure World.
   - Careful: the attested window is flash (0x08060000). Flash can't be written by a plain DMA store; it needs the FLASH controller program sequence. Don't over-claim; describe DMA protection as the platform assumption (like VECODI) plus GTZC configuration.
2. **Faults / attacks that are orthogonal → out of scope.**
   - Physical attacks, fault injection, side channels and DoS are "orthogonal to this work and require dedicated countermeasures" (same wording pattern as VECODI §3.1 Out-of-Scope Attacks).
3. **Fault during attestation → fail-closed policy (reset device). [confirm]**
   - If the Secure World hits a HardFault/SecureFault it cannot recover from, it resets the device, so no valid report is produced and Vrf treats the prover as not attested (timeout / invalid report = reject).
   - This is a deployment policy, not a new mechanism.
   - Firmware fact: `HardFault_Handler`, `BusFault_Handler`, `UsageFault_Handler` and `MemManage_Handler` are the CubeMX defaults (`while(1)`, i.e. halt). `SecureFault_Handler` calls a registered NS callback, else halts. 4. **Exceptions / NMI text. [confirm location: Background (TrustZone-M) vs Evaluation/Implementation]**

### Firmware findings while preparing R3.4 (2026-09-27) — discuss with advisor

1. **SMARM+FPE permutation bug (critical).** `ff1_speck.c` (identical in `ff1`, `ff1_runtime`, `ff1-energy`) `FF1EncryptBinary_Speck` keeps A and B in one bit buffer; when the bit length is odd (u ≠ v) the even round reads A with v bits and the second `memcpy` overwrites one bit of the new A, so one bit is lost per round and the map is not a bijection. `thesis/_ff1_bijection.py` (line-by-line port) shows coverage ≈ 50% of blocks for B = 64, 256, 1024, 4096 (13/11/9/7 bits); correct for B = 128, 512, 2048 (even bits). Cycle-walking also uses `tweak + 1` instead of re-encrypting under the same tweak (not a bijection for non-power-of-2 n; never triggered here because every evaluated n is a power of 2).
   - **Confirmed with the real C code:** `thesis/_ff1_host/` compiles the unmodified `ff1_speck.c` + `speck.c` from branch `ff1` on the PC (`python -m ziglang cc`) and runs the same loop as the firmware. Hash calls = n for every B, but distinct blocks measured: B=64 51.6%, B=256 51.6%, B=1024 53.1%, B=4096 37.5%; B=128/512/2048 100%.
   - Fix: separate A (u bits) / B (v bits), alternate m = u / v, `A, B = B, c`; cycle-walk with the same tweak. `thesis/_ff1_fixed.py` confirms a bijection for all n and exactly 10 PRF calls per index for power-of-2 n (same as the buggy code), so the per-block cost is unchanged. Runtime/energy numbers are therefore representative of the fixed code, but block coverage in the evaluated prototype was wrong for odd bit lengths.
2. **IRQ disable commented out in FPE.** `ff1` and `ff1_runtime` have `// __disable_irq();` around the block hash (only `ff1-energy` has it enabled). Student (2026-09-27): FAR was measured following the algorithm, i.e., with interrupts disabled during each block hash; the committed runtime builds simply have it commented out. The artifact release must restore it.
3. **Domain separation not in firmware.** All branches use the same `key` for the order seed (`HMAC(key, chal)` → AES-128 key/IV) and for the attestation HMAC. The paper now describes k_prp / k_mac (R1.4). Firmware must be updated for the artifact (cost: two short HMACs per round, constant).
4. **FindKthZero** scans all n bits but has data-dependent branches (`if bit==0 { if count==k ... }`), so it is not strictly constant-time (R3.3). A branchless version is needed before claiming constant time.
5. **Facts for R3.4:** seed = HMAC-SHA256(key, chal) → 16-B AES key + 16-B IV; PRNG = AES-128-CTR on zero blocks, 32-bit words; RandInt = rejection sampling (accept r < n·⌊(2³²−1)/n⌋, return r mod n; unbiased); SMARM = Fisher–Yates with that RandInt; FPE = FF1-style radix-2 Feistel, 10 rounds, PRF = CBC-MAC with Speck128/128 (32 rounds), key = first 16 B of the HMAC output, tweak = first 4 bytes of chal (public). The P/Q encoding does not follow SP 800-38G byte-for-byte, so the paper must not claim NIST FF1 compliance.
