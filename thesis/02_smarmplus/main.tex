\begin{abstract}
Remote attestation (RA) detects software compromise on IoT devices, but
classical RA keeps interrupts disabled for a full memory (hash) measurement and can block real-time work for hundreds of milliseconds.
SMARM instead measures memory in a secret shuffled order, so attestation can be interrupted between blocks while still resisting
\emph{roving malware}.
As a result, SMARM reduces the uninterruptibility period from a full memory measurement to a single-block measurement.
Despite this improvement, this period can be non-negligible for large block sizes, making SMARM less ideal for deadline-driven settings.
In this work, we propose two independent enhancements to SMARM that reduce this uninterruptibility period even further.
The first, called \emph{\smarmcopy}, disables interrupts only around a short memory copy into Secure memory, then hashes the copied block with interrupts enabled.
The second, \emph{\smarmlock}, instead makes the target block ephemerally unavailable to Non-Secure software during an
in-place hash, with no copy buffer.
% On STM32L552ZE with FreeRTOS, both substantially reduce the per-block
% interrupt-disabled window for block sizes up to $B{=}4096$~bytes;
% using the Frequency Accuracy Ratio (FAR) from prior FreeRTOS/TrustZone-M
% SMARM work, we also observe FAR~$\approx 1.0$ under a $1000$~Hz workload.
On STM32L552ZE with FreeRTOS, both substantially reduce the uninterruptibility period even for larger blocks: by about one order of magnitude with \smarmcopy{} and by roughly two to three orders of magnitude with \smarmlock.
\end{abstract}

\section{Introduction}
\label{sec:intro}

Modern societies increasingly depend on Internet-of-Things (IoT) devices across domains ranging from smart factories, where industrial sensors support monitoring and automation, to smart homes, where devices such as smart lights and robotic vacuum cleaners improve convenience. 
Since many IoT devices are designed to be inexpensive and energy-efficient, they typically operate on resource-constrained microcontrollers (MCUs) with limited RAM, flash storage, and energy budgets. These constraints often preclude sophisticated monolithic operating systems and the malware defenses available on higher-end devices.

Remote attestation (RA)~\cite{eldefrawy2012smart,nunes2019vrased,eldefrawy2017hydra} has emerged as an inexpensive technique for detecting malware compromise on resource-constrained IoT devices. In RA, an IoT device, called the \emph{prover}, executes a measurement routine that hashes its software image (i.e., the code stored in flash memory) and returns the measurement result in an authenticated response, e.g., using a message authentication code (MAC). 
An external trusted party, called the \emph{verifier}, authenticates this response and then compares the measurement against that of the expected software image to determine whether the prover's software has been modified and hence whether a malware compromise has occurred on the prover.

Traditional RA requires the measurement routine to execute atomically with interrupts disabled. This atomic execution is necessary to prevent \emph{roving malware} from evading detection by relocating itself to a region that has already been measured. On low-end MCUs, however, the resulting uninterruptibility period can exceed $450$~ms~\cite{nunes2019vrased}. Such prolonged interrupt disablement can severely interfere with real-time applications whose correctness depends on completing time-critical tasks within their deadlines.

To relax the atomicity requirement, SMARM~\cite{carpent2018smarm} introduces a new technique, called \emph{shuffled measurement}, which permits interrupts between the measurements of individual memory blocks. To defend against roving malware, SMARM measures the blocks comprising the software image in a random and secret order. Since malware does not know which blocks have already been measured, it cannot reliably relocate itself to an inspected block to evade detection. Although this approach does not provide the deterministic protection of fully atomic measurement, it makes evasion probabilistically difficult while reducing the uninterruptibility period from the measurement of the entire software image to that of a single block.

Despite this improvement, SMARM's maximum uninterruptibility period remains determined by its block size. Prior work~\cite{smarmplus2026,carpent2018smarm} shows that using larger blocks can reduce the total attestation time by lowering per-block processing overhead. However, a larger block also takes longer to measure, thereby extending each uninterruptible period and potentially delaying time-critical tasks beyond their deadlines. Conversely, smaller blocks shorten these intervals but increase the number of blocks and the associated computational overhead, resulting in longer attestation times and greater energy consumption. SMARM therefore exposes an inherent tradeoff between real-time responsiveness and energy efficiency, which is particularly problematic for battery-powered IoT devices.


Motivated by this observation, we propose two independent enhancements to shuffled measurement that further shorten its uninterruptibility periods, allowing the technique to coexist with a broader range of time-sensitive applications.
Our contributions are as follows:

\begin{itemize}
\item We propose \smarmcopy, which reduces each uninterruptibility period from the time required to hash one memory block to the substantially shorter time required to take a snapshot of (i.e., perform a memory copy of) that block.

 

\item \smarmcopy incurs additional Secure memory to hold a copied block. To relax this constraint, we propose \smarmlock, which uses interrupt disablement only for temporarily changing the security attribute of the memory block without copying its contents.
As an additional benefit, \smarmlock further reduces the uninterruptibility period, at the cost of introducing a probability of interference with concurrent application memory accesses.


\item We implement \smarmcopy and \smarmlock on an STM32 Nucleo-144 board (STM32L552ZE, Cortex-M33 with TrustZone-M)~\cite{stm32nucleo144} running FreeRTOS and evaluate them on real hardware. Our results demonstrate that both mechanisms substantially reduce SMARM's non-interruptible periods, thereby improving its compatibility with time-sensitive embedded applications.


\end{itemize}



\section{Background}
\label{sec:background}

\subsection{RA Atomicity and SMARM}

%\oak{Briefly mention RA workflow, i.e., challenge-response between prover and verifier etc.}
At a high level, remote attestation (RA) is a challenge--response
protocol between a \emph{prover} (i.e., a resource-constrained IoT device in this work) and a trusted \emph{verifier}.
The verifier sends a fresh challenge (e.g., a random nonce); 
the prover computes an authenticated integrity measurement, typically using a message authentication code (MAC), over its software image together with that challenge and a pre-shared attestation key $k$ and returns it as attestation evidence. 
The verifier then checks the evidence using the verification key against a reference value for the expected software state.
Classical RA techniques often \emph{disable interrupts} for the whole measurement so that \emph{roving malware} cannot move itself while memory is being hashed~\cite{eldefrawy2012smart,nunes2019vrased}.
This makes those techniques undesirable for time-sensitive or deadline-driven settings.

To address this, SMARM~\cite{carpent2018smarm} instead derives a one-time permutation $\sigma$ from the verifier challenge and an attestation key $k$, then measures blocks $M_{\sigma(i)}$ one by one, re-enabling interrupts between blocks.
The security claim is not ``malware cannot interrupt''; it is that without knowledge of the remaining secret order, malware cannot reliably relocate to escape detection, and repeated independent sessions drive the escape probability down~\cite{carpent2018smarm}.
SMARM requires the following security properties:
\begin{enumerate}
  \item[\textbf{[S1]}] \textbf{Controlled Execution.}
    The attestation function (i.e., the authenticated integrity and measurement routines) is reachable only through defined
    entry/exit points. Interrupts may be re-enabled only
    \emph{between} block measurements so malware cannot relocate itself during a block measurement.
  \item[\textbf{[S2]}] \textbf{Key Secrecy.}
    The attestation key $k$ is stored in memory inaccessible to
    untrusted software, so malware cannot obtain it to directly forge a valid report without triggering the attestation routine.
  \item[\textbf{[S3]}] \textbf{Private Measurement Order.}
    The permutation $\sigma$ is stored in memory inaccessible to malware such that the malware cannot predict which remaining blocks will be measured next and relocate before or after each block measurement.
\end{enumerate}
The original SMARM design builds on the HYDRA attestation architecture to satisfy these properties~\cite{eldefrawy2017hydra}.


\subsection{ARM TrustZone-M}


ARM TrustZone-M for Cortex-M~\cite{trustzone2025,an5347} partitions the
MCU into a \emph{Secure} world (trusted code and secrets) and a
\emph{Non-Secure} world (RTOS and applications).
The IDAU (fixed) and programmable SAU attribute each address range as
Secure, Non-Secure, or Non-Secure Callable (NSC); memory not explicitly
marked Non-Secure is \emph{Secure by default}, and Non-Secure software
may reach Secure services only through NSC entry points.
Our target devices provide eight programmable SAU regions. 

Recent work~\cite{smarmplus2026} adapts SMARM to coexist with an RTOS (e.g., FreeRTOS~\cite{freertos2025}) while leveraging TrustZone-M to preserve SMARM's security guarantees. In this design, FreeRTOS and application tasks execute in the Non-Secure world, while the SMARM service, attestation key~$k$, and secret permutation~$\sigma$ reside in the Secure world. 
A Non-Secure wrapper (as a real-time task) may invoke the SMARM service through an NSC entry point, as illustrated in Fig.~\ref{fig:system_model}. During attestation, interrupts are enabled between consecutive block measurements, allowing the RTOS to schedule other tasks, including high-priority real-time workloads. We use this TrustZone-M-based SMARM design~\cite{smarmplus2026} as the \emph{baseline} for this work.

\section{Design}
\label{sec:design}

\subsection{Motivation}
\label{sec:motivation}

In the SMARM baseline, interrupts must be disabled throughout the measurement of each memory block. Consequently, the uninterruptibility period (\tdis), during which real-time tasks cannot execute, is determined by the time required to measure a single block. This duration depends primarily on two factors: the block size ($B$) and the measurement function.
%
Following prior work~\cite{smarmplus2026,carpent2018smarm}, we investigated this issue using SHA-256 as the underlying measurement function. On an STM32 Nucleo-144 board, we observe that \tdis increases with $B$, from $0.062$~ms at $B{=}64$~bytes to $3.75$~ms at $B{=}4096$~bytes. For comparison, a high-frequency real-time task running at $1000$~Hz has a period of only 1~ms. Thus, with $B{=}4096$~bytes, a single SMARM block measurement can
span several task periods and cause the real-time task to miss multiple
deadlines. This makes the baseline SMARM unsuitable for such
time-sensitive workloads
(as also observed in prior FreeRTOS/TrustZone-M SMARM
work~\cite{smarmplus2026}).

In this work, we observe that \tdis can be reduced without compromising SMARM's functionality or security guarantees. In particular, we notice that the security of each block measurement (in \textbf{[S1]}) inherently requires a \emph{temporal consistency} property~\cite{carpent2018temporal} in which the measurement result must faithfully correspond to a consistent state of the measured block at some point during the measurement.
The SMARM baseline achieves this property by measuring each block atomically with interrupts disabled, thereby preventing untrusted software from modifying the block while its contents are being hashed.

\emph{However, disabling interrupts throughout the entire measurement is not the only way to fulfill this property.}
The key requirement is instead to ensure a consistent \emph{capture} of the block contents that serve as input to the hash. Based on this observation, we propose two alternative mechanisms, \smarmcopy and \smarmlock, that preserve such consistency while substantially shortening the uninterruptibility period and allowing the hash computation itself to remain interruptible. Figure~\ref{fig:timing_diagram} compares their uninterruptibility periods with those of traditional RA and the SMARM baseline.

\subsection{System and Threat Model}
\label{sec:system_threat}
We follow the system and threat models of prior work~\cite{smarmplus2026}. The prover is a resource-constrained IoT device equipped with a TrustZone-M TEE. 
It runs a commodity RTOS and application tasks in the Non-Secure world, while a small Trusted Computing Base (TCB), including the attestation service and its security-critical state, resides in the Secure world. 
The remote verifier is trusted and aims to determine the integrity of the prover's software while minimizing interference with real-time tasks scheduled to run intermittently on the prover device.

We consider a software-level adversary (i.e., malware) with full control over the Non-Secure world, including the RTOS and applications. In particular, the adversary may employ \emph{roving malware} that relocates its malicious code or data during an ongoing attestation in an attempt to evade measurement. The Secure world and its TCB are trusted; thus, the adversary cannot compromise or modify code, data, or secrets residing in Secure memory.
We consider hardware attacks, including attacks that directly manipulate the hardware-enforced security attribution provided by the SAU/IDAU, to be out of scope.

\subsection{\smarmcopy}
\label{sec:atomic}

Our first enhancement achieves temporal consistency by taking an atomic snapshot of the shuffled memory block to be measured ($M_{\sigma[i]}$) and storing the snapshot in Secure-world RAM, where it is inaccessible to untrusted Non-Secure software. The subsequent measurement is then performed over this protected copy. We refer to this enhancement as \smarmcopy.

As illustrated in Fig.~\ref{fig:combined_workflow}, \smarmcopy follows the same overall workflow as the SMARM baseline and differs only in the per-block measurement operation. Rather than disabling interrupts for the entire measurement of $M_{\sigma[i]}$, \smarmcopy disables interrupts only while copying $M_{\sigma[i]}$ into Secure-world RAM.
Since the copy is performed atomically, the resulting snapshot corresponds to a consistent state of $M_{\sigma[i]}$.
Once the snapshot is complete, interrupts can be re-enabled and the measurement function can operate on the Secure copy without interference from untrusted software.

The direct benefit of \smarmcopy is that it substantially shortens the uninterruptibility period, since \tdis is reduced from the time required to hash a block to the time required only to copy it. On our Cortex-M33 target, the memory-copy throughput is around $17$~MB/s, giving
$t_{\mathrm{disabled}}^{\mathrm{copy}}\approx B/(17~\mathrm{MB/s})$, which is about $15\times$ shorter than the corresponding \tdis of the SMARM baseline.
%
The main drawback of \smarmcopy is its additional memory requirement since it requires a Secure-world storage of size $B$ to hold the snapshot. Our second enhancement, presented next, eliminates this additional storage.



\subsection{\smarmlock}
\label{sec:sau}

While \smarmcopy achieves temporal consistency by copying each block into a Secure-world buffer, this requires an additional $B$ bytes of Secure RAM. Our second enhancement, \smarmlock, avoids this storage overhead by making the memory block being measured, $M_{\sigma[i]}$, \emph{ephemerally inaccessible} to untrusted software.
This allows the SMARM service to measure the block \emph{in place} while interrupts remain enabled.

In our target system, we leverage the SAU to realize this mechanism. As shown in Fig.~\ref{fig:combined_workflow}, before measuring $M_{\sigma[i]}$, \smarmlock reconfigures the SAU regions covering the attested memory so that $M_{\sigma[i]}$ is excluded from Non-Secure coverage.
%The SAU configurations before and during block measurement are shown in Figure~\ref{fig:sau_memory_map}. 
Since memory not explicitly attributed as Non-Secure is considered to be Secure by default in TrustZone-M, this effectively makes $M_{\sigma[i]}$ accessible only from the Secure world. 
The SAU update is followed by data and instruction synchronization barriers (\texttt{DSB} and \texttt{ISB}) to ensure that the new memory-security attribution takes effect immediately.

To preserve temporal consistency, the SAU reconfiguration and the associated barriers must execute atomically with interrupts disabled. However, this atomic operation is substantially shorter than either hashing or copying the entire block.
In our measurements, each SAU attribution update takes only
$0.80$--$1.30\,\mu$s ($87$--$143$ cycles at $110$~MHz).
Once the block has been guarded, interrupts are re-enabled and the SMARM service measures $M_{\sigma[i]}$ directly. During this period, Non-Secure software may continue executing but cannot access or modify the protected block.

After the measurement completes, the SMARM service briefly disables interrupts again to restore the original SAU configuration and make $M_{\sigma[i]}$ Non-Secure again, and then proceeds to the next shuffled block $M_{\sigma[i+1]}$.
Thus, \smarmlock reduces each uninterruptibility period to a short SAU reconfiguration operation while keeping the substantially longer measurement computation interruptible. Unlike \smarmcopy, it also requires no additional Secure-world buffer of size $B$.

\subsection{Security Guarantees}
\label{sec:security_summary}

Both \smarmcopy and \smarmlock modify only how each shuffled memory block is measured; they do not alter the underlying SMARM protocol. In particular, the attestation key $k$ and secret permutation $\sigma$ are generated, used, and stored exactly as in the SMARM baseline. Therefore, \textbf{[S2] Key Secrecy} and \textbf{[S3] Private Measurement Order} continue to hold. 
Likewise, both designs preserve SMARM's controlled execution interface, where the attestation functionality remains within the Secure-world SMARM Service and can be invoked from the Non-Secure world only through its designated NSC entry point.

The main change concerns \textbf{[S1] Controlled Execution}. In the SMARM baseline, interrupts are disabled throughout the measurement of each block, preventing malware from modifying or relocating the block while it is being hashed.
Our designs shorten this uninterruptibility period while preserving the same requirement as follows:

\begin{itemize}
    \item \smarmcopy achieves this by disabling interrupts only while $M_{\sigma[i]}$ is copied into Secure-world RAM. Since this snapshot is taken atomically, it represents a consistent state of the block. Once the copy completes, interrupts can safely be re-enabled.
    This is because even if malware subsequently modifies or relocates the original Non-Secure contents, such changes cannot affect the snapshot already stored in Secure RAM. The measurement thus operates on a consistent and protected representation of $M_{\sigma[i]}$.

    \item \smarmlock achieves the same property without creating a snapshot. Before measuring $M_{\sigma[i]}$, the SMARM service atomically reconfigures the SAU so that the block becomes inaccessible to Non-Secure software. Interrupts can then be re-enabled while the block is measured in place, since malware cannot access the protected block during this period. After the measurement completes, the SMARM service atomically restores the original SAU configuration before proceeding to the next block.
\end{itemize}




Thus, \smarmcopy and \smarmlock preserve \textbf{[S1]} through two different mechanisms.
As such, with the unchanged guarantees of \textbf{[S2]} and \textbf{[S3]}, both enhancements retain the security guarantees of the SMARM baseline while substantially reducing its uninterruptibility period.



\section{Evaluation}
\label{sec:eval}

\subsection{Setup}

We evaluate the SMARM baseline, \smarmcopy, and \smarmlock on an STM32 Nucleo-144 development board equipped with a Cortex-M33 MCU and TrustZone-M. The MCU runs at $110$~MHz and executes FreeRTOS and real-time applications in the Non-Secure world. 
We configure $512$~KiB of Non-Secure flash as the attested memory region, yielding the total attested memory size of $|M|{=}512$~KiB.
We evaluate all three designs across six block sizes,
$B\in\{128,256,512,1024,2048,4096\}$~bytes; we use the following evaluation metrics: the uninterruptibility period (\tdis), real-time availability, additional Secure-world RAM, and an end-to-end attestation runtime.

\subsection{Uninterruptibility Period}

Figure~\ref{fig:tdisabled} compares \tdis{} of the SMARM baseline, \smarmcopy, and \smarmlock{} on a logarithmic scale. Across all three designs, \tdis{} increases with the block size $B$, as larger blocks require more work during the corresponding uninterruptible operation.

Compared with the baseline, \smarmcopy{} reduces \tdis{} by approximately one order of magnitude (about $15\times$) by replacing the per-block hash within the interrupt-disabled period with a substantially faster memory copy. At $B{=}4096$~bytes, \tdis{} decreases from $3.75$~ms in the baseline to about $0.24$~ms with \smarmcopy{} (Fig.~\ref{fig:tdisabled}).


\smarmlock{} further reduces \tdis{} by limiting interrupt disablement to the short SAU reconfiguration operations required to protect and restore each block. At $B{=}4096$~bytes, \tdis{} is around $0.8$--$1.3\,\mu$s, corresponding to a reduction of roughly three orders of magnitude compared with the baseline.

Overall, these results show that \smarmcopy{} and \smarmlock{} substantially shorten SMARM's uninterruptibility period, reducing it from the millisecond range in the baseline to the sub-millisecond and microsecond ranges, respectively.

\subsection{Secure Memory Overhead}

\smarmcopy incurs additional Secure-world RAM overhead because each block must be copied into a protected buffer before it is measured. This overhead is exactly equal to the block size $B$, since the buffer must be large enough to hold one complete memory block.
In contrast, \smarmlock does not require a copy of the measured block and therefore introduces no additional Secure-world RAM overhead beyond that already required by the SMARM baseline. 


\subsection{Real-Time Availability}

We evaluate real-time availability using the Frequency Accuracy Ratio (FAR) metric proposed in~\cite{smarmplus2026}, defined as:
\begin{align*}
    \mathrm{FAR} = f_{\mathrm{observed}} / f_{\mathrm{baseline}}
\end{align*}
where $f_{\mathrm{observed}}$ is the observed execution frequency of a periodic real-time task while attestation is active, and $f_{\mathrm{baseline}}$ is its execution frequency under the same attestation workload but with interrupts enabled during block measurement. Thus, $\mathrm{FAR}\approx1.0$ indicates that attestation introduces little interference with the execution frequency of the real-time task, whereas a lower FAR indicates increasing interference.

As shown in~\cite{smarmplus2026}, under a $1000$~Hz real-time workload, the FAR of the SMARM baseline decreases significantly as $B$ increases, particularly when \tdis becomes longer than the task period. 
In contrast, both \smarmcopy{} and \smarmlock{} maintain $\mathrm{FAR}\approx1.0$ across all evaluated block sizes, including $B{=}4096$~bytes. These results show that the substantial reductions in \tdis{} achieved by our enhancements translate directly into improved real-time availability, allowing high-frequency real-time tasks to continue executing with negligible interference during attestation.


\subsection{Attestation Runtime}
Reducing \tdis{} does not proportionally shorten a full attestation round:
the HMAC over $|M|{=}512$~KiB still dominates wall-clock time.
Table~\ref{tab:attest_runtime} reports the mean duration of one Secure shuffled HMAC call with no concurrent real-time task (ten rounds per configuration).
Across these sizes the three designs remain in the same ballpark, from about $480$~ms at $B{=}4096$ to about $567$--$592$~ms at $B{=}128$.
Sample standard deviation over the ten rounds is below $1$~ms for every cell (often exactly~$0$).
\smarmcopy{} is consistently about $30$~ms slower than the baseline because it copies the hashed bytes before HMAC (IRQ on).
\smarmlock{} adds only a short SAU update per block (IRQ off), then hashes with interrupts enabled; the SAU work is microseconds per block and does not show up as a large end-to-end gap.
Baseline SMARM and \smarmlock{} therefore differ by only a few milliseconds; this paper does not claim that \smarmlock{} is faster.
The intended tradeoff is a shorter \tdis{}, not a shorter attestation round.

Table~\ref{tab:ra_comparison} summarizes our two enhancements and compares them with traditional RA and the SMARM baseline. Both \smarmcopy{} and \smarmlock{} substantially reduce \tdis{}, making them well suited to real-time applications with RTOS support. In particular, \smarmlock{} reduces \tdis{} to the microsecond range, making the attestation process nearly fully interruptible.

These improvements, however, come with different trade-offs. \smarmcopy{} requires an additional Secure-world buffer of size $B$ to store the snapshot. In contrast, \smarmlock{} requires no additional Secure-world RAM, but ephemerally makes the block under measurement inaccessible to Non-Secure software. Consequently, a concurrent Non-Secure task that attempts to access this block during its measurement may experience a fault, which could indirectly affect its real-time execution. This represents a trade-off between Secure-memory overhead and potential memory-access interference. In practice, \smarmlock{} is therefore most suitable when the attested region can tolerate such faults, whereas \smarmcopy{} provides a preferable alternative when uninterrupted Non-Secure access to the attested memory is required.

\section{Related Work}
\label{sec:related}

Traditional RA techniques~\cite{eldefrawy2012smart,nunes2019vrased,eldefrawy2017hydra} commonly disable interrupts throughout the entire memory measurement to preserve temporal consistency and prevent malware from modifying or relocating itself during attestation. However, the resulting long uninterruptible period can interfere with time-sensitive operations.

SMARM~\cite{carpent2018smarm}, PRoM~\cite{aman2021prom}, and HAtt~\cite{aman2018hatt} relax this requirement through \emph{shuffled measurement}, allowing interrupts between consecutive block measurements. Nevertheless, each individual block measurement must still execute atomically, leaving an uninterruptible period whose duration depends on the block-measurement time.
Our work is complementary to these approaches and specifically targets this remaining per-block uninterruptibility.

Other attestation techniques have explored different mechanisms for supporting interrupts during security-critical execution. ISC-FLAT~\cite{isc-flat} and ASAP~\cite{asap} enable interrupts during runtime attestation by leveraging a TEE to securely account for interrupt execution while preserving the authenticity of the resulting runtime (e.g., control-flow) evidence.
IDA~\cite{ida2024}, in contrast, uses trusted hardware monitoring to verify that the attestation procedure executes correctly without requiring interrupts to remain disabled.
LO-FAT~\cite{lo-fat}, LiteHAX~\cite{litehax}, and ATRIUM~\cite{atrium} remove uninterruptible periods via dedicated hardware support.
These approaches primarily target runtime or hardware-assisted attestation.
In contrast, our work focuses on reducing the remaining uninterruptibility of \emph{shuffled memory measurement} on commodity TrustZone-M hardware without requiring custom hardware support.

\section{Conclusion}
\label{sec:conclusion}
SMARM improves remote attestation for real-time systems by allowing
interrupts between memory blocks, but hashing each block with interrupts
disabled can still stall time-critical work when blocks are large.
We propose two complementary enhancements on FreeRTOS with TrustZone-M.
\smarmcopy{} shortens the interrupt-disabled window to a brief Secure-world
memory copy, then hashes with interrupts enabled; it needs a Secure buffer
the size of one block and adds roughly thirty milliseconds to a full
attestation round.
\smarmlock{} shortens that window further without the buffer by briefly
making each block unavailable to Non-Secure software through SAU updates,
then hashing the block in place with interrupts enabled.
Both preserve SMARM's security goals.
Prefer \smarmcopy{} when Secure RAM is available or the SAU must stay fixed
after boot; prefer \smarmlock{} when a dedicated Non-Secure data region can
host short SAU changes during attestation.
